## Sheet replacement and roster checks (2026-11-14)

| #    | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Rule in                                                                                                |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| RP1  | **A replacement replaces the term's data for good.** It applies only when a pending sheet is promoted and its spreadsheet differs from the one that last fed the term (the active sheet, or after Remove the last disabled one that synced). Re-connecting the same spreadsheet keeps the same-sheet rules. In the pending-sheet transaction, before the import: every enrollment of every offering of the term (with marks, score history and comments) is deleted; offerings the new sheet does not feed are deleted with their criteria, schemes and program links (tab mappings pointing at them become `REMOVED`); offerings it keeps stay (id, visibility, criteria, weights); SHEET term enrollments go, an admin's assignment stays for a student the new `ALL` lists; all the term's student issues and the other sources' previews go. Then the normal import runs into the clean term. Other terms are never touched | `packages/sync/src/replacement.ts`                                                                     |

The triggers allow DELETE of score history, non-draft schemes and their items only for rows of that term. `audit_logs` has its own trigger and never honours these flags                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | migration `20261114120000_term_replacement`                                                            |
| RP3  | The deletion set (offering ids, account ids, counts) is computed by one function the preview and the sync both call. An ID the new sheet lists is created again as a new PENDING account. ## Session rules (2026-11-17)

| #   | Decision | Where |
| --- | -------- | ----- |
| SR1 | **One session per user (Rule A).** A successful login (after password, status and temporary-password checks) locks the user row, revokes every other active session of the user (`SIGNED_IN_ELSEWHERE`, sessions and refresh tokens) and creates the new one in one transaction; audit `auth.sessions.replaced` with `revokedCount` when any were ended. Students and admins alike. Failed logins change nothing. Refresh locks the session row and re-checks everything, so a racing refresh cannot keep the old session. 401 `SESSION_REPLACED`. | `auth.service.ts` login; `session.service.ts` rotate |
| SR2 | **Inactivity logout (Rule B).** `SESSION_IDLE_TIMEOUT_SECONDS` (900). Only `POST /auth/heartbeat` is activity (user decision 2); refresh and other routes are not. The web app sends it from a visible tab every `SESSION_HEARTBEAT_INTERVAL_SECONDS` (300, at most idle / 3), one per browser. A session found idle is revoked on the spot (`IDLE_TIMEOUT`), 401 `SESSION_IDLE`; a heartbeat never revives it. | `auth_sessions.last_activity_at`; migration `20261117120000_session_rules` |
| SR3 | **No positive cache (user decision 1).** Every request reads the session by primary key; the 5 s `ssrs:v1:auth:valid:*` cache is removed. The denylist `ssrs:v1:auth:revoked:{sid}` (value = reason) stays as a fast reject only; Redis down means PostgreSQL answers. Every revocation also sets `refresh_tokens.revoked_at` in the same transaction, then denylists and publishes `ssrs:v1:auth:session-ended` after commit and before the response. | `session.service.ts` checkSession / announce |
| SR4 | **Live connection.** `GET /auth/live` is a server-sent event stream (checked through the Next.js dev proxy and `next start`: events arrive unbuffered). `ended` with `SIGNED_IN_ELSEWHERE` / `IDLE_TIMEOUT` / `REVOKED` only, no ids. One Redis subscriber per API process; a 10 s database re-check covers lost messages, Redis outages and idle expiry; the stream closes without `ended` at access-token expiry. Caddy does not compress it. | `session-events.ts`, `live.service.ts`, `deploy/Caddyfile` |
| SR5 | **Live limits.** `LIVE_MAX_PER_SESSION` (3) and `LIVE_MAX_PER_USER` (5) open streams; extra → 429 `TOO_MANY_LIVE_CONNECTIONS`. Counted across instances in Redis sorted sets whose members expire after 60 s unless renewed (a dropped connection or crashed process cannot leak a slot); per-process counts while Redis is down. | `live-slots.ts` |
